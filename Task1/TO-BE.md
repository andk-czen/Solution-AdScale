#Архитектура AdScale. Целевое решение (To_BE)
Система эволюционирует из монолита в микросервисную архитектуру с событийно-ориентированным взаимодействием. Целевое решение достигается в результате применения шаблона Strangler Fig в течение 12 месяцев.
Целевая архитектура полностью избавляется от монолита и представляет собой 8 независимых сервисов. При развертывании применяется подход георезерва и региональное распределение.
Прогнозируемо система должна достигать заявленных характеристик в 50000 RPS, P99 latency < 50ms и SLA 99,9%.

Взаимодействие разделено на 2 типа: синхронное (gRPC/HTTPS) для critical path процессов и асинхронное (Kafka) для обмена данными между сервисами (изменение данных о кампаниях, таргетинг, ставки, статистика, аналитика, отчеты).

API шлюз обеспечивает единую точку входа, балансирует нагрузку, обеспечивает маршрутизацию и безопасность аутентификации.

Выделено 2 независимых шлюза для разделения внешнего трафика:
- API gateway DSP (HTTPS/OpenRTB) — прием bid request от DSP партнеров
- API-gateway (HTTPS) — для взаимодействия с конечными пользователями

##Сервисы
Поскольку при проектировании целевой архитектуры применён шаблон Strangler Fig, то границы самих сервисов оставлены практически без изменений.
- bidding service — сервис ставок. Подбирает рекламу, взаимодействует с DSP. Рекламные
кампании, таргетинг, ставки, правила, конфигурации. БД PostgreSQL. Кеш — Redis. Наиболее
зависимый от latency сервис.
- campaign service — сервис кампаний. Рекламные кампании, ставки, таргетинг, не влияет на
поток процесса аукциона. Реплицирование (чтение с реплики) для снижения нагрузки на
master. БД PostgreSQL.
- auction service — сервис аукциона. Взвешивает рекламу. БД PostgreSQL. Кеш — Redis.
- delivery service — сервис выдачи. Формирование разметки баннера. БД PostgreSQL. Кеш —
Redis.
- statistic service — сервис статистики. БД ClickHouse — клики, показы. Асинхронный,
минимальное влияние на latency процесса аукциона.
- financial service — финансовый сервис (баланс, счета, списания, транзакции, аудит операций,
отчеты). БД PostgreSQL. Поддержка и реализация ACID-транзакций. Асинхронная обработка
событий по финансовым операциям.
- analytics service — сервис аналитики. БД ClickHouse — хранилище событий для аналитики.
- advertiser service — пользовательский интерфейс, рекламный кабинет. Web-приложение. БД
PostgreSQL для хранения настроек интерфейса пользователей.

## Обработка событий, обмен между сервисами
Показы и клики пишутся в топик Kafka, а не напрямую в БД.
- campaign service → bidding-service — обновление ставок
- campaign service → bidding-service — обновление таргетинга
- campaign service → bidding-service, delivery service — кампании
- statistic service → analytics service, financial service — отображения рекламы
- statistic service → analytics service, financial service — события кликов
Остальные события читаются из Kafka и пишутся в БД батчами, что понижает нагрузку записи
с hot path процессов.

**Наличие асинхронного взаимодействия обеспечивает:**
- слабую связность между сервисами
- равномерно распределяет нагрузку
- снижает время ожидания
- повышает надежность (гарантии доставки)
- позволяет выполнять независимое масштабирование

## Хранение данных
Каждый сервис использует собственный компонент для хранения данных (Database per Service), что устраняет основную причину текущего решения — использование единой базы данных и конкуренцию за ресурсы. 
Для хранения данных статистики и аналитики используется ClickHouse.
Для хранения горячих данных (таргетинг, кампании, остатки бюджета) используется Redis.

## Использование кеширования
Использование Redis для кеширования позволяет снизить нагрузку с операционной БД PostgreSQL и позволяет повысить скорость чтения данных, снижая latency.

## Развертывание
В целевом решении за счет распределенной микросервисной архитектуры есть возможность независимого деплоя - каждый сервис может изменяться и масштабироваться отдельно.
