#ADR-002 Выделение сервиса ставок в качестве первого приоритета
Для достижения поставленных бизнес целей в рамках модернизации архитектуры и перехода на микросервисы принято решение применять паттерн Stanger fig - выделять по одному сервису из монолита. Необходимо определить какой сервис будет иметь наивысший приоритет и будет выделен первым.

Кандидаты:
- Bidding service - сервис ставок
- analytics service - сервис аналитики
- campaign service - сервис кампаний
- financial service - финансовый сервис

**Текущие показатели**
15000 RPS в пике при пределе системы P95 времени отклика 110-120 ms

**Ключевые архитектурные драйверы**
нагрузка: 18000 RPS в пике с увеличением до 50000 RPS
Задержка: <100 ms
Доступность: SLA 99,9%

**Критерии выбора**
- критичность - компонент должен иметь высокую критичность и являться "узким местом" в цепочке процессов.
- независимость - компонент должен иметь минимальное кол-во зависимостей
- изолируемость - компонент может быть изолирован за интерфейсом взаимодействия - для компонента можно выделить четкие границы для взаимодействия по api
- влияние - выделение компонента должно оказывать существенный прирост производительности

**Решение**
Bidding service представляет собой (повторяет) функционал рекламного сервера, но с возможностью внешней интеграции. Bidding service создается как отдельный независимый сервис и закрывается от внешних запросов api шлюзом (api gateway).
Для работы сервиса формируется кеш в Redis.

**Обоснование решения**
Первым для выделения из монолита выбран Bidding service, поскольку:
- критичность: сервис находится на критическом пути процесса. сервис является входной точкой для получения запросов по ставкам и является начальной точкой всего бизнес-процесса аукциона. Для этого процесса указан SLA <=80 ms.
- независимость: компонент имеет минимальное кол-во зависимостей, для которых можно реализовать публичные интерфейсы. Имеет выделенную изолированную БД
- изолируемость: сервис изолирован от взаимодействия с другими компонентами за api интерфейсом. На входе используется OpenRTB, на выходе - gRPC.
- влияние: выделение компонента в отдельный сервис с использвоание кеша, очередей и gRPC должно оказать существенный прирост производительности.

Выделение из монолита именно сервиса ставок Bidding service позволяет обеспечить дальнейший рост RPS с 18000 до 50000 без масштабирования всего монолита полностью.

##Последствия

**Положительные**
- Обеспечение целевых показателей производительности и устойчивости к нагрузке.
- Повышение latency и пропускной способности операций на критическом пути.
- Возможность выполнить бизнес-цель - подключить систему DSP в указанные сроки = 3 месяца.

**Отрицательные**
Необходим прогрев кеша. Без наполнения кеша данными система не будет работать на максимально возможной расчитанной производительности.
Требуется мониторинг обновления и работы кеша (Redis).

**Риски**
Кеш превращается в высоко критичный компонент системы, для которого следует обеспечить высокую устойчивость к сбоям, восстанавливаемость и наблюдаемость.

##Критерии проверки
Решение успешно, если после выделения сервиса система при 18000 RPS выдерживает P95 <= 100 без сбоев и падения производительности.
