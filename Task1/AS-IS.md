# AS-IS анализ (диагностика текущей архитектуры)
Платформа AdScale - гибридный монолит (C++/Go/Python/Node), развернутый на одном production-кластере с использованием БД PostgreSQL (одна инстанция). 
Кэш и очереди отсутствуют. Деплой выполняется вручную.
Бизнес цель: интеграция с крупной DSP-площадкой, что добавит +20% трафика сразу и приведет к двукратному увеличению через год. Нарушение SLA приведет к штрафам и финансовым потерям.
Ключевая проблема: система работает на пределе своих технических возможностей и в текущем состоянии не способна предоставить заявленные возможности и удовлетворить требуемые SLA.

## Монолитное приложение, состоит из следующих компонентов:
| Компонент | Язык | Назначение | Значение и влияние|
|---|---|---|---|
| Ad Server (Рекламный сервер) | C++/Go | Приём HTTP запросов, идентификация пользователей, подбор кандидатов | критичен по latency  |
| Auction Engine (Сервер аукциона) | C++ | применяет бизнес-правила для взвешивания ставок и определения победителя |  Наиболее чувствителен к задержкам |
| Delivery Service (Сервис выдачи) | Node | готовит разметку баннера, формирует response | критичный функционал |
| Statistics Service (Сервис статистики) | Python | собирает данные по событиям: запись кликов и показов | создаёт высокую write-нагрузку  |
| Financial Service (Финансовый сервис) | Go | списание средств, выставление счетов и сведение балансов | Платежные транзакции, критичный функционал |
| Analytics Service (Сервис аналитики) | Python | собирает аналитику | Тежелыми запросами создает блокировки и рост latency |
| Advertiser Dashboard (Рекламный кабинет) | Node |пользовательский интерфейс (UI) для рекламодателей | Не критичный функционал |

## Атрибуты качества, метрики
| Метрика | Текущее значение | Требование |
|---|---|---|
| Нагрузка: кол-во запросов | 15 000 RPS | 18000 c увеличением до 50000 |
| P95  времени отклика | 110-120 ms | <= 100 ms |
Наблюдаются периодические деградации в часы пик.
Выявлено отсутствие запаса по производительности.

## Узкие места 
- Единая БД для всех сервисов и операций
- Одна инстация БД
- Отсутствие разделения операций записи и чтения данных из БД
- Ручной деплой, один кластер
- Рекламный сервер критичен по latency
- Сервер аукциона использует синхронные вызовы к БД
- Сервис статистики работает напрямую с ПРОД базой, создавая высокую нагрузку
- Сервис аналитики создает тяжелые запросы на ПРОД БД и попрождает блокировки и рост latency
 
## Точки отказа
 - Единая БД
 - Единственный кластер, на котором развернута вся система
 
## Архитектурные проблемы, препятствующие масштабированию
- Единая БД в одном экземпляре
- синхронные взаимодействия
- отсутствие кеширования данных
- "монолит" затрудняет горизонтальное масштабирование

 
## Влияние текущей архитектуры на время отклика
- все сервисы используют одну БД, что увеличивает нагрузку на неё, порождает конкуренцию за ресурсы и повышает время отклика
- некоторые сервисы отправляют тяжелые запросы и увеличивают время обработки и время отклика для параллельных запросов других сервисов
- использование синхронных запросов требует дополнительного времени на ожидание ответа и повышает время отклика
