# Стратегия Database per Service
Согласно стратегии каждый микросервис должен иметь свой источник для хранения данных и иметь возможность управлять им единолично.

## Сервис ставок (Bidding Service)
Тип БД: PostgreSQL + Redis 
**Обоснование**
Для долгого хранения холодных данных используется PostgreSQL. Для горячих данных - оперативные данные с быстрым доступом (кеш) - используется Redis.

## Сервис кампаний (Campaign Service)
Тип БД: PostgreSQL + Redis 
**Обоснование**
Для долгого хранения холодных данных используется PostgreSQL. Для горячих данных - оперативные данные с быстрым доступом (кеш) - используется Redis.

## Сервис статистики (Statistic Service)
Тип БД: ClickHouse
**Обоснование**
Большие массивы информации (50 000 показов/кликов в секунду). Возможности колоночного хранения повышают скорость доступа к большим данным.
Не требуется изменение данных, только чтение и запись.


## Сервис аналитики (Analytics Service)
Тип БД: PostgreSQL + ClickHouse
**Обоснование**
Большие массивы информации (50 000 показов/кликов в секунду). Возможности колоночного хранения повышают скорость доступа к большим данным.
Не требуется изменение данных, только чтение и запись.
Возможности реляционной СУБД для хранения настроек аналитики, агрегированных готовых отчетов в виде реляционных таблиц.


## Сервис финансов (Financial Service)
Тип БД: PostgreSQL  (с репликацией)
**Обоснование**
Возможности реляционной СУБД для хранения финансовых данных, связей между отношениями "пользователей" и "платежей". Гарантии ACID. Поддержка и возможности constraint особенно необходимы для финансов.
