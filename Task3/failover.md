
# Отказоустойчивость
***RPO и RTO для каждого сервиса, стратегия резервного копирования, соответствие принципам 12-факторных приложений***

RPO (Recovery Point Objective) — допустимый объём потери данных, выраженный во времени/
RTO (Recovery Time Objective) - это максимальное допустимое время простоя, в течение которого ИТ-система, сервис могут оставаться недоступными после сбоя.

|Сервис / хранилище|RPO|RTO|Механизм|Обоснование|
|---|---|---|---|---|
|Financial| стремится к нулю| минуты | Синхронная/semi-sync репликация на standby + WAL-архив + "восстановление на момент времени»" | Потеря финансовой информации и транзакций критична и недопустима |
|Campaign| минуты | минуты/десятки минут | Async Master-Slave, периодические снапшоты | Потеря редактирования кампании иногда допустима|
|Bidding (кэш)| секунды | секунды | Реплики + AOF/snapshot; восстановление из источников | Данные не критичны, поскольку кэш это копия и могут быть восстановлены, но сильно влияют на скорость работы системы |
|Stats| минуты | минуты/часы | Репликация, шардирование| Потерянные данные могут быть восстановлены повторной обработкой событий из Kafka|
|Analytics| часы | часы | Перестроение витрин из Stats/событий | Данные не критичные, можно восстановить и пересчитать |



## Cоответствие принципам 12-факторных приложений
***Проверка соответстия принципам после перехода на новую микросервисную архитектуру***


**1. Codebase (Кодовая база)**
Соответствие: Одно приложение — одна кодовая база.
Выгода: чёткое разделение ответственности, независимые релизы, изоляция ошибок.

**2. Dependencies (Зависимости)**
Соответствие: все зависимости явно объявлены.
Выгода: воспроизводимость сборок, отсутствие ситуаций работы только на локалке.

**3. Config (Конфигурация)**
Соответствие: конфигурация не в коде, а во внешних источниках, секреты через Kubernetes Secrets.
Выгода: один и тот же образ Docker работает в dev/staging/prod + корректировка без релиза.

**4. Backing Services (Сторонние службы)**
Соответствие: БД, кэш, очереди — как привязанные ресурсы, сервисы обращаются к PostgreSQL, Redis, Kafka по URL из конфигурации, не из кода.

**5. Build, Release, Run (Сборка, релиз, запуск)**
Соответствие: чёткое разделение фаз.
Реализация: сборка: CI/CD‑пайплайн создаёт Docker‑образ; релиз: образ + конфигурация --> Kubernetes Deployment; запуск: Pod в Kubernetes.
Выгода: атомарные релизы, возможность быстрого отката без аффекта на смежные сервисы.

**6. Processes (Процессы)**
Соответствие: процессы не хранят состояние локально.
Выгода: горизонтальное масштабирование, быстрое восстановление после сбоя.

**7. Port Binding (Привязка портов)**
Соответствие: сервисы самодостаточно запускаются как веб‑сервисы.
Реализация: каждый сервис слушает HTTP‑порт (например, :8080).
Выгода: сервис можно запустить локально и проверить; API Gateway может проксировать.

**8. Concurrency (Параллелизм)**
Соответствие: масштабирование через процессы/контейнеры => горизонтальное масштабирование в Kubernetes (HPA/VPA).
Выгода: рост нагрузки обрабатывается добавлением реплик.

**9. Disposability (Утилизируемость)**
Соответствие: быстрые старт и остановка.
Выгода: устойчивость к сбоям нод.

**10.Dev/Prod Parity (Паритет сред разработки и продакшена)**
Соответствие: окружение разработки максимально близко к продакшену.
Реализация: Docker Compose; одинаковые версии БД, Redis, Kafka в dev и prod; те же конфигурации (только значения переменных окружения разные).
Выгода: меньше багов при деплое, быстрая отладка.

**11. Logs (Журналирование)**
Соответствие: логи — поток событий.
Реализация: сервисы пишут логи в stdout; сбор логов через Logstash → Elasticsearch; визуализация через Kibana; структурированные логи (JSON) с request_id, service_name.
Выгода: централизованный мониторинг, своевременное реагирование, настройка алертов.

**12. Admin Processes (Админ-процессы)**
Соответствие: одноразовые задачи запускаются в окружении релиза.
Выгода: обеспечивает консистентность и упрощает управление системой.
