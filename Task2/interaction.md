# Схема взаимодействия с обоснованием выбора протоколов
**Протоколы и паттерны взаимодействия**

Для внешнего обмена данными с DSP-партнером используется протокол OpenRTB. Протокол взаимодействия: HTTPS. Формат данных: JSON.
Изменение протокола не планируется, т.к. выбранный протокол является стандартом для данной предметной области и задач подобного рода.
Для внутреннего обмена между сервисами выбран протокол gRPC как наиболее быстрый вариант взаимодействия, в сравнении с REST.

**Преимущества при выборе gRPC:**
- производительность при использвоании protobuf и использовании сериализации
- строгие контракты, исключает дополнительные ошибки в данных
- использование HTTP/2 позволяет использовать сжатие, мультиплексирование

**Недостатки при выборе gRPC:**
использование бинарного формата вместо json - хуже читаемость, сложнее разработка, сложнее поддержка и сопровождение кода

**Для обмена событиями выбран kafka:**
- оптимально при высоких нагрузках, возможность организовать буфер событий для сглаживания пиков
- возможность получить гарантию доставки
- для обмена с некритическими сервисами есть возможность через необходимое рвемя прочитать повторно сообщение, отправленное ранее.

Для авторизации и маршрутизации используется API gateway. Взаимодействие внешнего клиента с API gateway выполняется по http (rest).
API gateway выполняет:
- аутентификацию
- маршрутизацию
- защищает систему от нагрузки при неработающих компонентах/сервисах - реализует паттерн circuit breaker 
- логирует все операции аутентификации клиентов в едином месте
- предоставляет возможности единой балансировки запросов (rate limiting)

Без единого api шлюза многие из этих операций были бы невозможны или их пришлось бы реализовывать в каждом сервисе отдельно.

Rest используется там, где не критично время отклика, важна простота и совместимость при разработке.
gRPC используется там, где важна высокая производительность, минимальное время отклика.
