
# Спецификация сервиса ставок bidding service 

Сервис выделяется из текущего монолита, т.к. находится на критическом пути и сильно зависит от задержек (latency), влияет на итоговый SLA системы.

## Границы 
Сервис должен повторять и дополнять функционал уже существующего рекламного сервера Ad Server, но с возможностью получения запросов от DSP путём добавленой интеграции.
**Входит в границы сервиса:**
- приём bid запросов от DSP партнёра по HTTPS/OpenRTB
- проверка и обработка полученного запроса
- чтение существующих кампаний из БД (Redis)
- формирование и предача bid ответа по HTTPS/OpenRTB
- определение пользователей, подбор кандидатов
- преедача данных в AuctionEngine (gRPC)

**Взаимодействие с другими компонентами/сервисами:**
- API gateway - аутентификация DSP, безопасность, маршрутизация
- AuctionEngine - взвешивает ставки, определяет победителя
- Campaign Service (new) - управление кампаниями, ставками, таргетингом
- Kafka - публикация финальных событий для оповещения других сервисов

Необходимо исключить из взаимодействия медленные асинхронные вызовы и синхронные вызовы с долгим ожиданием ответа.
Для этих целей используется кеш Redis, а для передачи тяжелых данных - очередь в Kafka.

### Алгоритм взаимодействия 
1. DSP через api шлюз обращается к bidding service
2. bidding service получает данные о кампаниях и их настройках из Redis
3. bidding service передает запрос в AuctionEngine
4. AuctionEngine взвешивает ставки, определяет победителя, возвращает ответ в bidding service
5. bidding service возвращает bid ответ от DSP
6. bidding Service публикует событие показа в Kafka

## API
Необходимо предусмотреть 2 варианта api: внешний api для взаимодействия с DSP и внутренний для взаимодействия с сервисами
Внешний api: REST - обработка bid request и возврат bid response, использование протокола OpenRTB. Требуемое время отклика 100 мс.
Внутренний api: gRPC для взаимодействия с AuctionEngine, kafka для взаимодействия с другими сервисами и получения обновленных данных по кампаниям, обновление кеша.

**request - метод POST rtb/bids**
авторизация: JWT token
параметры запроса:
- id
- banner-type
- baner-size
- target-region
- device-type
- ip-client

Параметры ответа при успешном статусе (200)
- id
- price
- alt-text
- url

Если запрос не может быть обработан успешно - возврат стандартного статуса ошибки 4xx или 5xx - в зависимости от типа.

## Зависимости от других сервисов
- CampaignService - сервис, хранящий данные по кампаниям. Для передачи в bidding service используется кеш в Redis
- AuctionEngine - сервис, реализующий работу со ставками: взвешивает ставки, определяет победителя, возвращшает ответ в bidding service.

## Модель данных
кампании (Campaigns): id, название, описание, статус, дата начала, дата окончания, id рекламодателя
рекламодатели (advert_agents): id, название, описание, контакты, реквизиты
ставки (bids): id, id кампании, значение ставки
настройки таргетинга (targetings): id, id кампании, название настройки, значениие настройки


# Патерны надежности

## Circuit Breaker - для вызовов зависимых сервисов
Алгоритм:
**Closed (закрыт)** (нормальное состояние): запросы проходят, выполняется фиксация и подсчет возникающих ошибок
**Open (разомкнут)** при превышении лимита ошибок к сервису (например, 25% ошибок за последние 1000 запросов) все запросы остальные запросы сразу отклоняются. В ответ отправляется статус 503 (Service Unavailable). На определенный промежуток времени сервис становится недоступен.
**Half‑Open** затем через заданный интервал T (например 10–20 сек) пропускается часть запросов. Если в течение какого-то недолгого времени эта часть запросов завершается успехом, то ограничитель переводится в состояние Closed и снова принимает все запросы. Если нет — снова перевод в состояние Open.
**Пороги:** доля ошибок в %, доля таймаутов, насыщение пула.


## Retry Pattern - повторные попытки с экспоненциальной задержкой
Используется в случаях:
- При таймаутах в обращении к другому сервису
- При возникновении ошибок 5xx, полученных от внешней системы или сервиса
- При использвоании брокеров сообщений во взаимодействиях
- При ограниченных ресурсах (превышение лимита)

**Алгоритм:** 
Задержка возрастает экспоненциально с джиттером (рандомизацией), чтобы избежать потока запросов, когда все клиенты одновременно начинают отправлять запросы.
 

## Идемпотентность финансовых операций и резервные стратегии (кэшированные или дефолтные ставки) 
Финансовые операции должны быть идемпотентными: повторный вызов с теми же параметрами не должен приводить к двойному списанию.
Для обеспечения идемпотентности операций применяется ключ идемпотентности - уникальный идентификатор, передаваемый в каждом запросе и сохраняемый сервисом.
При повторной отправке сообщения с тем же ранее использованным ключом сервис возвращет ответ с ошибкой нарушения уникальности.

***Дедупликация:**
- в Redis - для быстрой проверки дублей на hot path при резервировании бюджета;
- в Financial Service - уникальный констрейнт в транзакционной БД: повторная попытка списать тот же токен

**Резервные стратегии**

***Дефолтная ставка (Default Bid):***
Использовать дефолтные, заранее настроенные, значения ставок на случай, если невозможно получить актуальное новое значение.
Если сервис Auction Engine недоступен - используется дефолтное значение. Таким образом сервис получит значение и успешный ответ, а не долгое ожидание или ошибку.

***Кэшированные ставки:***
Сформировать кеш и разместить его в Redis - для хранения наиболее востребованных значений. Настроить время хранения и обновления.
Первично ответ отправляется из кеша. Кеш обновляется по истечении времени хранения.

***Ручная обработка отклоненных запросов и событий:***
Если событие не удаётся обработать после N попыток - оно направляется в отдельный топик Kafka, откуда будет извлечено и обработано вручную.
