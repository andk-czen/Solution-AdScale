# API Gateway
API Gateway - единая точка входа для DSP. Предоставляет возможности аутентификации, ограничения частоты запросов, маршрутизации запросов, мониторинга времени отклика и является автоматическим размыкателем.
Основная цель использования и реализации API Gateway  - изолировать Bidding Service от перегрузки при выполнении непрофильных операций, тем самым поддерживая SLA на требуемом уровне.

Для API Gateway предполагается использовать готовое промышленное решение. Возможные варианты: Envoy, Kong, аналоги. Окончательный выбор будет сделан на стадии согласования и финальной разработки тех.проекта. 

## Маршрутизация запросов на ставки
Выполняется стредствами встроенного механизма API Gateway.
Стандартные средства API Gateway позволяют задать следующие параметры и настройки маршрутизации:
- путь
- метод
- целевой адресуемый url
- timeout

## Ограничение частоты запросов**
Ограничение частоты запросов используется для защиты сервиса и системы от перегрузки и соблюдения SLA.
Использование Rate limiting через API Gateway позволяет ограничивать весь трафик глобально, а не отдельно на каждом сервисе.
Запросы можно ограничивать как на клиента в сек/минуту, так и на api-ключ или для выбранного ip-адреса или диапазона ip-адресов. Подобные махинизм также защищает систему от DDoS-атак.

**Вариант настройки и реализации:**
- допускаются короткие всплески, ограничивается средний темп
- задается RPS на каждого DSP и общий RPS на отрезок времени
- при превышении - статус `HTTP 429 Too Many Requests` с заголовком `Retry-After`
- выделяются сегменты низкоприоритетного, основного и высокоприоритетного трафика
- при росте премени ожидания выполняется сброс обработки низкоприоритетного трафика, чтобы поддержать обработку основного высокоприоритетного

## Аутентификация
Аутентификация выполняется централизованно средствами API Gateway, а не в каждом сервисе отдельно. 
Для аутентификации в API Gateway используется JWT-токен. Если токен невалиден, Gateway возвращает ошибку 401, и сервис не узнает о неавторизованном запросе.
Подобный подход дополнительно ограничивает сервис от неадресных невалидных запросов, тем самым снижая нагрузку на сервис.

## Автоматический размыкатель (Circuit Breaker)
Паттерн защищает от каскадных отказов. При превышении количества допустимых ошибок срабатывает механизм, который отключает прием и обработку новых запросов.
На отправленные клиентом запросы в течение заданного времени сервер будет отправлять статус (503) с указанием детальной информации о том, через сколько можно повторить попытку запроса.
Для обработки Retry-запросов рассматривается вариант "Экспоненциальный backoff с джиттером", позволяющий избежать одновременных повторов и распределить  во времени обработку повторных запросов.


## Мониторинг времени отклика
Время отклика (как и прочие метрики) могут быть выставлены на мониторинг.
В настройках Gateway задается порог задержки на весь запрос. Любой запрос, не уложившийся в указанные пороги,
прерывается и возвращается fallback. 
При возникновении такой ситуации N раз подряд - сервис отмечается как неработающий и к нему применяются алгоритмы и методы снижения нагрузки через Circuit Breaker.
Возникшие события могут быть записаны в отдельные таблицы и выведены на дашборд для удобства наблюдения. При приближении к границам и превышении метрик - вывод соответствующих предупреждений.

*Варианты используемых дополнительных метрик:*
- http_request_duration_seconds — гистограмма времени ожидания
- http_status_code_total — количество ответов по HTTP-кодам
- bandwidth_bytes — трафик
- over_latency - нарушения порогов latency
- error rate (5xx) - возникшие ошибки 5xx на сервере
